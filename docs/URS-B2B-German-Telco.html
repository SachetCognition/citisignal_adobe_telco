1. Executive Summary

This User Requirements Specification (URS) defines the functional and non-functional requirements for transforming the existing CitiSignal B2C storefront into a fully-featured B2B Telco Storefront targeting German enterprise customers.

The current CitiSignal implementation is built on Adobe Edge Delivery Services (EDS) with Adobe Commerce SaaS Drop-in components, using a block-based architecture (see blocks/ directory) and a three-phase loading pipeline (loadEager / loadLazy / loadDelayed in scripts/scripts.js). The transformation will extend this foundation with B2B commerce capabilities including company accounts, shared catalogs, quote negotiation, purchase-order approval workflows, and German-market localization (de_DE).

The target users are German Mittelstand and enterprise companies purchasing corporate mobile contracts (Mobilfunkverträge), fixed-line packages, IoT SIM solutions, and device-as-a-service offerings. The storefront will comply with German legal requirements (DSGVO, Impressum, AGB) and support B2B payment methods prevalent in Germany (SEPA-Lastschrift, Rechnung, Vorkasse).

2. Scope & Objectives

In Scope

  • B2B company account management with German business identifiers (HRB, USt-IdNr)
  • Full German localization (de_DE) — UI, currency, tax, legal pages
  • Shared catalogs with customer-specific and tiered pricing
  • Quote request, negotiation, and quote-to-order workflows
  • Requisition lists and reordering capabilities
  • Multi-level purchase-order approval workflows
  • German B2B payment methods (SEPA, Rechnung, Vorkasse)
  • Telco-specific features: fleet SIM management, contract lifecycle, DaaS
  • Self-service Kundenportal with KPIs, user management, support tickets
  • DSGVO/GDPR compliance, WCAG 2.1 AA / BITV 2.0 accessibility
  • Integration touch-points for SAP ERP, CRM, and corporate SSO

Out of Scope

  • B2C consumer-facing storefront modifications
  • Non-German market localizations (other than English fallback)
  • Physical retail / POS integration
  • Full SAP ERP implementation (only integration interface is defined)
  • Mobile native app development (responsive web only)

5. Company Account Management

URS-FR-001 Company Registration with German Business Identifiers P1 Planned

The system shall support company registration requiring a Handelsregisternummer (HRB) and USt-IdNr (VAT ID). VAT IDs shall be validated in real-time via the EU VIES service. Registration shall be rejected if VIES validation fails.

URS-FR-002 Company Organizational Hierarchy P1 Planned

The system shall support a multi-level organizational hierarchy within each company account: Geschäftsführer (Managing Director), Abteilungsleiter (Department Head), Einkäufer (Buyer), and Mitarbeiter (Employee). Parent-child relationships between organizational units shall be configurable by the company admin.

URS-FR-003 Role-Based Access Control P1 Planned

The system shall enforce role-based access control with the following roles: Admin (full company management), Buyer (create orders and quotes), Approver (approve/reject purchase orders), and Viewer (read-only catalog and order history access). Permissions shall be configurable per role.

URS-FR-004 Multiple Shipping/Billing Addresses (German Format) P2 Planned

Each company account shall support multiple shipping and billing addresses using the German address format: Straße (Street), PLZ (Postal Code), Ort (City), Bundesland (Federal State). Addresses shall be assignable to specific organizational units or cost centers.

URS-FR-005 Company Credit Limit Management (Kreditlimit) P2 Planned

The system shall support configurable credit limits (Kreditlimit) per company account. Orders that would exceed the remaining credit balance shall be blocked at checkout with an appropriate German-language error message. Credit limit status shall be visible on the company dashboard.

6. German Localization (de_DE)

URS-FR-006 Full German Language UI P1 Planned

All UI elements shall be rendered in German, including block content, navigation, checkout flows, error messages, form labels, and system notifications. The store view shall be configured as de_DE via the configs.js environment detection system.

URS-FR-007 EUR Currency with German Number Formatting P1 Planned

All monetary values shall be displayed in EUR using German number formatting: 1.234,56 € (period as thousands separator, comma as decimal separator, Euro sign after the amount).

URS-FR-008 German Tax Display P1 Planned

Product prices shall display both Brutto (gross) and Netto (net) amounts. The standard VAT rate of 19% MwSt and reduced rate of 7% shall be applied and shown. Invoices shall include a full tax breakdown.

URS-FR-009 German-Compliant Legal Pages P1 Planned

The storefront shall include the following legally required pages: Impressum (Legal Notice), AGB (Allgemeine Geschäftsbedingungen / General Terms), Datenschutzerklärung (DSGVO/Privacy Policy), and Widerrufsbelehrung (Cancellation Policy). All pages shall be accessible from the footer navigation.

URS-FR-010 German Date Format & Phone Validation P2 Planned

Dates shall be displayed in DD.MM.YYYY format throughout the application. Phone number fields shall validate the German international format (+49 prefix).

7. B2B Catalog & Pricing

URS-FR-011 Shared Catalogs with Custom Pricing (Rahmenverträge) P1 Planned

The system shall support shared catalogs per company with custom pricing tiers (Rahmenverträge / framework agreements). Each company shall only see products and prices assigned to their catalog.

URS-FR-012 Volume / Tiered Pricing P1 Planned

The system shall support volume-based and tiered pricing for corporate plans and bulk device orders. Price tiers shall be clearly displayed on the product detail page (e.g., 1–9 units, 10–49, 50–99, 100+).

URS-FR-013 Corporate Telco Product Types P1 Planned

The catalog shall support the following corporate telco product types: Mobilfunkverträge (mobile contracts), Festnetz (landline), Internet packages, IoT SIM packages, and Fleet SIM management bundles.

URS-FR-014 Product Comparison with SLA Tiers P2 Planned

The system shall provide a product comparison feature for enterprise plans with clearly differentiated SLA tiers: Bronze, Silber, Gold, and Platin.

URS-FR-015 Quick Order / CSV Bulk Upload P2 Planned

The system shall support a quick-order form and CSV bulk upload functionality for multi-SIM provisioning. Uploaded CSVs shall be validated, and errors shall be reported per line with German-language messages.

8. Quotation & Negotiation

URS-FR-016 Request for Quote (Angebotsanfrage) Workflow P1 Planned

Buyers shall be able to submit a Request for Quote (RFQ / Angebotsanfrage) from the cart. The RFQ shall capture requested quantities, desired pricing, and any special terms.

URS-FR-017 Negotiable Quotes with Multi-Round Negotiation P1 Planned

The system shall support negotiable quotes with multi-round negotiation between buyer and sales representative. Features include line-item discounts, overall quote discounts, comments per round, and configurable expiration dates.

URS-FR-018 Quote-to-Order Conversion P1 Planned

Accepted quotes shall be convertible to orders with a single action. The order shall inherit all negotiated prices and terms from the accepted quote.

URS-FR-019 Quote PDF Generation in German P2 Planned

The system shall generate quote PDFs in German with company letterhead, all line items, negotiated prices, terms & conditions, and validity period.

9. Requisition Lists & Reordering

URS-FR-020 Multiple Requisition Lists (Bestelllisten) P2 Planned

Each user shall be able to create and manage multiple requisition lists (Bestelllisten) for organizing frequently ordered products by department, project, or purpose.

URS-FR-021 Add-to-Requisition-List from PDP and PLP P2 Planned

Users shall be able to add products to a requisition list directly from the Product Detail Page (PDP) and Product Listing Page (PLP). A list selector shall appear when multiple lists exist.

URS-FR-022 Requisition List to Cart Conversion P2 Planned

Users shall be able to move all items (or selected items) from a requisition list to the shopping cart in a single action.

URS-FR-023 Reorder from Order History P3 Planned

Users shall be able to reorder all items from a previous order with a single click from the order history view.

10. Purchase Orders & Approval Workflows

URS-FR-024 Purchase Order (Bestellanforderung) Creation P1 Planned

The system shall support purchase order creation with a mandatory PO number field. PO numbers shall follow a configurable format per company.

URS-FR-025 Multi-Level Approval Workflows P1 Planned

The system shall enforce multi-level approval workflows based on order value thresholds:

Order ValueApproval Required
< 500 €Auto-approved
500 – 5.000 €Abteilungsleiter (Department Head)
> 5.000 €Geschäftsführer (Managing Director)

Thresholds shall be configurable per company.

URS-FR-026 Approval / Rejection with Comments P1 Planned

Approvers shall be able to approve or reject purchase orders with mandatory comments on rejection. The full approval history with timestamps shall be visible on the order detail page.

URS-FR-027 Email Notifications for Pending Approvals P2 Planned

The system shall send email notifications in German to the designated approver when a purchase order is pending approval. Reminder emails shall be sent after a configurable period.

11. Checkout & Payment (German B2B)

URS-FR-028 B2B Checkout with Company Address Pre-fill P1 Planned

The B2B checkout shall pre-fill the company's default shipping and billing addresses. Additional fields shall include PO number and cost center selection (Kostenstelle).

URS-FR-029 German B2B Payment Methods P1 Planned

The system shall support the following B2B payment methods:

  • SEPA-Lastschrift (Direct Debit) with IBAN validation (DE format: DE + 2 check digits + 18 digits)
  • Rechnung (Invoice / Net 30 payment terms)
  • Vorkasse (Prepayment / Bank Transfer)

URS-FR-030 Split Billing per Cost Center P2 Planned

The system shall support split billing, generating separate invoices per cost center or department within a single order.

URS-FR-031 Recurring Billing for Contract Services P2 Planned

The system shall support recurring billing setup for contract-based services (e.g., monthly mobile contract fees). Billing frequency and contract duration shall be configurable.

12. B2B Telco-Specific Features

URS-FR-032 Corporate Fleet Management Dashboard P1 Planned

The system shall provide a fleet management dashboard displaying all active SIMs, their associated contracts, assigned employees, current status (active/suspended/cancelled), and aggregated usage data.

URS-FR-033 Multi-Line / Multi-SIM Ordering with Employee Assignment P1 Planned

Buyers shall be able to order multiple SIM cards in a single transaction and assign each SIM to a specific employee. The assignment data shall be passed to the provisioning system.

URS-FR-034 Contract Lifecycle Management P1 Planned

The system shall manage the full contract lifecycle including Vertragslaufzeit (contract duration: 12/24/36 months), renewal options, and cancellation with Kündigungsfrist (notice period) tracking. Users shall receive alerts before the cancellation deadline.

URS-FR-035 Device-as-a-Service (DaaS) P2 Planned

The system shall support Device-as-a-Service offerings with corporate leasing options. Leasing terms (12/24/36 months), monthly rates, and end-of-lease options (return, purchase, extend) shall be displayed on the product page.

URS-FR-036 Bulk Provisioning API Integration P2 Planned

The system shall integrate with the network provisioning API to support bulk SIM activation, number porting, and plan assignment for large orders.

URS-FR-037 Usage Reporting Dashboard per Cost Center P2 Planned

The system shall provide usage reporting dashboards filterable by cost center (Kostenstelle), showing data consumption, call minutes, SMS counts, and associated costs per billing period.

13. Self-Service Portal (Kundenportal)

URS-FR-038 Company Dashboard with KPIs P1 Planned

The company dashboard shall display key performance indicators including: active lines count, monthly spend (current and trend), contract overview (active, expiring soon, expired), and recent order activity.

URS-FR-039 User Management P1 Planned

Company admins shall be able to add and remove employee users, assign roles, and manage permissions. New users shall receive an activation email in German.

URS-FR-040 Order History with Filtering & Export P2 Planned

The order history view shall support filtering by date range, status, cost center, and order value. Export to CSV and PDF formats shall be available.

URS-FR-041 Support Ticket Creation & Tracking P2 Planned

Users shall be able to create support tickets from the portal, categorize them (billing, technical, contract), and track their resolution status.

URS-FR-042 Document Center P3 Planned

The portal shall provide a document center where users can download invoices, contracts, SLA agreements, and other company documents in PDF format.

14. Non-Functional Requirements: Performance

URS-NFR-001 Largest Contentful Paint (LCP) P1 Planned

The storefront shall achieve an LCP of < 2.5 seconds on corporate network connections (50 Mbps+). This aligns with the existing LCP block prioritization in scripts/scripts.js.

URS-NFR-002 Concurrent B2B User Support P1 Planned

The system shall support 500+ concurrent B2B users per tenant without performance degradation.

URS-NFR-003 Catalog Search Performance P2 Planned

Catalog search queries shall return results in < 200 ms for catalogs containing 50,000+ SKUs.

15. Non-Functional Requirements: Security & Compliance

URS-NFR-004 DSGVO (GDPR) Compliance P1 Planned

The system shall be fully DSGVO-compliant, including: consent management platform integration, data deletion request handling, and a cookie banner compliant with § 25 TTDSG. No tracking shall occur before explicit consent.

URS-NFR-005 Role-Based Data Access P1 Planned

Users shall only be able to access data belonging to their own company. Cross-company data leakage shall be prevented at the API layer.

URS-NFR-006 Audit Logging P1 Planned

All purchase, approval, and user management actions shall be logged with timestamp, user ID, action type, and affected resources. Audit logs shall be retained for a minimum of 10 years per German commercial law (HGB § 257).

URS-NFR-007 Transport & Application Security P2 Planned

The system shall enforce TLS 1.3, implement Content Security Policy (CSP) headers, and include XSS protection mechanisms.

16. Non-Functional Requirements: Accessibility

URS-NFR-008 WCAG 2.1 AA Compliance P1 Planned

All storefront pages and components shall comply with WCAG 2.1 Level AA guidelines.

URS-NFR-009 German Screen Reader Compatibility P2 Planned

The storefront shall be tested for compatibility with German screen readers (JAWS, NVDA with German language pack). All ARIA labels shall have German translations.

URS-NFR-010 BITV 2.0 Compliance P1 Planned

The storefront shall comply with BITV 2.0 (Barrierefreie-Informationstechnik-Verordnung), the German federal regulation for accessible information technology.

17. Non-Functional Requirements: Integration

URS-NFR-011 Adobe Commerce B2B Module Integration P1 Planned

The storefront shall integrate with the Adobe Commerce B2B module for company accounts, shared catalogs, quotes, requisition lists, and purchase orders. B2B GraphQL queries shall follow the existing pattern in commerce.js using performCatalogServiceQuery and performMonolithGraphQLQuery.

URS-NFR-012 ERP Integration (SAP) P1 Planned

The system shall provide integration interfaces for SAP ERP for order and invoice synchronization. Order data shall be transmitted to SAP upon order placement, and invoice data shall be retrieved for display in the document center.

URS-NFR-013 CRM Integration P2 Planned

The system shall integrate with a CRM system for company and contact management, enabling synchronized customer data and activity history.

URS-NFR-014 Corporate SSO (SAML 2.0 / OpenID Connect) P1 Planned

The system shall support Single Sign-On via SAML 2.0 and OpenID Connect for corporate login, enabling employees to authenticate using their company identity provider.

18. Technical Architecture Notes

Existing Architecture Foundation

The current CitiSignal storefront is built on Adobe Edge Delivery Services with the following key architectural patterns that B2B extensions must follow:

Three-Phase Loading Pipeline

Defined in scripts/scripts.js, the loading pipeline consists of:

  • loadEager(doc) — Critical-path initialization: language setting, Drop-in initialization, LCP block loading, experimentation plugin eager phase.
  • loadLazy(doc) — Deferred loading: autolinking modals, loading remaining blocks, footer, CSS, experimentation lazy phase, commerce events SDK.
  • loadDelayed() — Non-critical resources loaded after a 3-second delay via delayed.js.

New B2B components must integrate into the appropriate phase. B2B-critical blocks (e.g., company account, checkout) should be added to the LCP_BLOCKS array when they are above the fold.

Block-Based Architecture

UI components reside in the blocks/ directory. Each block is a self-contained module with its own JS and CSS. Existing commerce blocks include:

  • commerce-cart, commerce-checkout, commerce-account
  • commerce-login, commerce-create-account
  • product-details, product-details-custom, product-details-plan
  • product-list-page, product-list-page-custom

New B2B blocks (e.g., b2b-company-dashboard, b2b-quote-negotiation, b2b-fleet-management) shall follow the same pattern.

Drop-in Component System

The head.html import map defines module aliases for Drop-in components:

  • @dropins/storefront-cart, @dropins/storefront-checkout
  • @dropins/storefront-pdp, @dropins/storefront-auth
  • @dropins/storefront-order-confirmation

B2B Drop-ins (e.g., @dropins/storefront-b2b-quotes, @dropins/storefront-b2b-requisition) shall be added to the import map and initialized via the same dropins.js initialization system.

Environment Configuration

The configs.js module provides environment detection (dev/stage/prod) based on the URL pattern. The de_DE store view configuration shall be added to the configs.xlsx sheet and accessed via getConfigValue().

GraphQL API Layer

The commerce.js module defines the GraphQL communication layer with two query execution paths:

  • performCatalogServiceQuery — High-performance Catalog Service API for product data (used by PLP/PDP).
  • performMonolithGraphQLQuery — Standard Adobe Commerce GraphQL API for transactional operations (cart, checkout, account).

B2B GraphQL queries (company management, quotes, requisition lists, purchase orders) shall be added following this same pattern, targeting the Monolith GraphQL endpoint for B2B module operations.
